## As built

This design is the record of the ideas stage and its body is left as it was written. The built app
differs from it in the places below; `docs/ARCHITECTURE.md` describes the code as it is now.

- **An unusable AI answer.** The design says a line whose answer still can't be used after the resend
  is recorded as "no match". Instead the line is left without a result and matching moves to matching
  failed, with a reason such as "The AI's answer for 2 lines could not be used"; Retry then rematches
  only the lines without a result (`app/steps/line_matching.py`). "No match" is kept for lines Claude
  itself says have no catalog item.
- **The headline latency.** The design names the time until the last result is stored as the logged
  figure. The headline figure is the on-screen time: from when the server receives Confirm until the
  review page reports that every result is on screen (`POST /invoices/{id}/shown` in
  `app/web/review.py`). The stored time is still recorded beside it, and every run also records when
  it ended, whatever its outcome. The README's Timings section reports both; matching the large
  invoice measured 8.4 seconds on screen cold and 7.3 seconds on a repeat.
- **Changing the metadata.** The design allows it from awaiting confirmation or in review. It is also
  allowed from matching failed (`app/web/confirm.py`, and the table of allowed moves in
  `app/status.py`). Changing it returns the invoice to awaiting confirmation; matching runs again only
  after the next Confirm.
- **The statuses.** There is no "Uploaded" status. The upload handler creates the invoice directly in
  extracting (`app/web/routes.py`), so there are seven statuses in all: extracting, extraction failed,
  awaiting confirmation, matching, matching failed, in review and finalized.
- **Docker Compose and settings.** The design calls the app a second service beside the reference API
  and says `.env.example` lists three settings. The app is the third of three Compose services (the
  reference database, the reference API and the app), and `.env.example` lists six settings: the
  three named plus `DATA_DIR`, `HOST` and `ALLOWED_HOSTS`. The `.env` file is optional to Compose, and
  `docker-compose.yml` sets the container's own reference API address, data folder and listening
  address, overriding `.env`. The app refuses to start without a key, from `app/__main__.py`.
- **The reference API.** Beyond the one-line SQLAlchemy fix, `docker-compose.yml` also binds the
  reference API's port 8000 and its database's port 5433 to `127.0.0.1` only, like the app's 8080.
- **Arithmetic warnings.** A skipped check, such as an invoice that prints no total or a line with a
  missing number, is shown as a note and is not counted as an arithmetic warning in the review and
  finalize summaries (`app/checks.py`). Amounts and totals are compared to the cent.
- **The finalize summary.** It also counts arithmetic warnings, so it reads like "3 lines with no
  match, 1 price difference, 0 arithmetic warnings" (`app/web/finalize.py`).
- **Tests.** Besides the stand-in tests and the real-Claude tests marked `live`, a third set marked
  `browser` drives a real browser through the running app with Playwright (`tests/browser/`). The
  plain `pytest` command leaves both costly sets out.
- **Next steps.** All seven next steps listed near the end of this document have been built.

## Problem Statement

Clinical trial sites (the hospitals and clinics that run a drug trial) bill the drug company paying
for the trial, called the sponsor. Each invoice has to be tied to the right sponsor, study and site,
and each billed line has to be checked against the list of approved items and prices for that
sponsor and study, called the catalog. Today that is manual reading and cross-checking.

We are building an app where a user uploads one invoice (a PDF or an image) and:

1. Claude reads it and pulls out the header facts (site, sponsor, study, protocol number, invoice
   number and date, and the printed total) and every billed line (description, quantity, unit price, amount).
2. The app matches the header facts to the provided reference API's sponsors, studies and sites,
   shows its suggestions with how sure it is, and waits. Nothing else happens until the user
   confirms or corrects them.
3. Once confirmed, the app fetches the catalog for that sponsor and study, and Claude suggests the
   catalog item for each line, or marks the line as having no match.
4. The user reviews the matches, can override any of them, and finalizes the invoice.

The point the take-home brief calls "the key insight" is that confirmation in step 2 is a hard gate:
the catalog depends on the confirmed sponsor and study, so line matching cannot start before it.

## Who it is for

- **The person using it:** someone in clinical trial finance or operations who checks site invoices
  before they are paid.
- **The people judging it:** ledgerrun reviewers. They will clone the repository, add an Anthropic API
  key, start it with one command, and push the four sample invoices through every stage. The design
  is aimed at what they will check: a gate that really holds, correct results on the samples, clear
  handling of the near-miss and unmatched cases, and a readable write-up.

## What Makes This Cool

The app is honest about what it doesn't know. On the mismatched-metadata invoice it doesn't say "not
found", and it doesn't quietly pick an answer either. It says something like: "the protocol printed
is NWD-VER-2024-002, which doesn't exist; the closest is NWD-VER-2023-002 (VERITAS), which differs
only in the year." On the large invoice it fills in matches line by line as they arrive, marks
"Patient Stipend" as having no catalog item, and flags the CT scan billed at $475 against a catalog
price of $450. The user can see why each suggestion was made and can fix it with one click.

## Constraints

- **Deadline:** about five days, finishing around 2026-10-25.
- **AI model:** Claude only, model `claude-opus-5-5`, with the model name set in an environment
  variable (from the decision on which AI model provider to use, D2).
- **Reference data:** only through the provided reference API, fetching every page of every list.
  Its address is a setting, `REFERENCE_API_URL`. Inside Docker Compose it is `http://api:8000` (the
  reference API's service name), because inside the app's container `localhost` means the app
  itself. When the app runs directly on the laptop it is `http://localhost:8000`. The app never reads that API's Postgres database or its seed files.
- **Real AI:** the running app always calls Claude and has no fake mode.
- **Starter code:** the reference API needed one fix to start (SQLAlchemy kept on the 2.0 series,
  from the decision on fixing the reference API, D1).
- **Repository:** public on GitHub and on Gauntlet's GitLab; one `git push` updates both.

## Premises

The author agreed to all five on 2026-10-20.

1. The audience is a reviewer running a demo, not production users. Success means the expected
   results on the four samples, a gate they can see working, and a clear write-up, not scale.
2. One user, no login, running on a laptop. Nothing is deployed. Everything starts with Docker
   Compose next to the reference API, which is also how it is delivered.
3. One app: a web page plus one backend. Extraction, metadata matching and line-item matching are
   separate modules inside that backend, each with its own entry point and tests, and the invoice's
   stored status decides which one may run. This meets the brief's "distinct steps or services".
4. The reference API is the only source of reference data, called over HTTP with every page
   fetched. The app's own data lives in its own small database.
5. Accuracy against the expected results (in `docs/PRD_REVIEW.md`) is the measure of quality, and
   prompt and approach choices are judged by it.

## Approaches Considered

### Approach A: One Python app with server-rendered pages (chosen)

Described in full under Recommended Approach. Effort: medium, about four days for a person or about
a day and a half of Claude Code build loop. Risk: low.

### Approach B: Separate front end, job worker and two-step matching

A React front end, a JSON API and a Redis job queue with a worker per stage, and a text-similarity
shortlist before Claude picks each line's match. Ruled out: about twice the work, and more for a
reviewer to install and more that can break within five days. The shortlist can also drop the right
item before Claude sees it.

### Approach C: Claude as an agent with tools

Claude searches the reference API with tools and explains its own matches. Ruled out: results vary
between runs, so they are hard to test against the expected results, and it is slower and costlier,
which works against the latency target.

## Recommended Approach

Approach A, recorded as the decision on the overall approach (D11).

### The parts

- **One web app in Python**, built with FastAPI (the same library the reference API uses). It serves
  plain HTML pages, and uses htmx (a small script that refreshes part of a page from the server) for
  progress. It runs as one extra service in the existing `docker-compose.yml`.
- **The app's own database is SQLite**, a single file. It stores invoices, the uploaded files'
  locations, extracted data, metadata suggestions, the confirmed metadata, line matches, overrides,
  the finalize summary and timings. The SQLite file and the uploaded files are kept on a named
  Docker volume, so past invoices survive the container being recreated.
- **A reference API client**: one small module that calls the reference API and always fetches
  every page (the large catalog has 100 items, and a plain request returns only the first 50).
  Every lookup goes through it, so tests can replace it with saved responses. It reads the
  reference API's address from the `REFERENCE_API_URL` setting.
- **Three pipeline modules, kept separate:**
  1. **Extraction** sends the uploaded file straight to Claude, a PDF as a document and an image as
     an image, so scans and photos work the same way as digital PDFs (from the decision on upload
     types, D7). Claude must answer in a fixed JSON shape (Claude's "structured outputs" feature).
     The extracted data includes the printed total. The app then checks the arithmetic: quantity
     times unit price against each line's amount, and the sum of the amounts against the printed
     total. If the invoice prints no total, the second check is skipped and the screen says so. Any
     mismatch is shown as a warning that the reading may be wrong.
  2. **Metadata matching** is ordinary code, not Claude. For each field it compares the invoice text
     with the reference records using fuzzy text comparison, plus exact checks on the protocol number,
     and gives a confidence level: exact, likely, uncertain or not found. It writes the reasons out
     plainly. It also checks that the fields fit together: the study must belong to the sponsor, and
     the site should take part in the study (according to the reference API's study-site links). If
     the sponsor isn't found but the study is, it suggests the study's own sponsor. If the suggested
     or chosen site is not linked to the study, the site's confidence drops by one level and a
     warning explains why, but Confirm is still allowed, since the links may be out of date. Nothing
     is ever confirmed automatically (from the decision on near-miss metadata, D8).
  3. **Line-item matching** runs only when the invoice's status says the metadata is confirmed. It
     fetches the confirmed sponsor and study's catalog, splits the invoice lines into groups of about
     five or six, and sends them to Claude. Every request starts with the same catalog text, so
     Claude can cache that part. Requests sent at the same instant cannot reuse a cache none of them
     has written yet, so the first group is sent alone to write the cache, and the remaining groups
     are then sent at the same time. Claude only caches a prompt start above a minimum length, so
     the small catalogs (4 to 10 items) may not be cached at all; the latency measurements will
     show whether caching applies. For each line Claude returns a catalog item ID or "no match", a
     confidence level (high, medium or low, a separate scale from the metadata levels, shown as a
     label beside each match), a short reason, and any close alternatives. Price breaks ties
     between similar items but never decides a match alone.
     - **Checking each answer:** every line in a group must get exactly one result, and every
       catalog ID must be in the fetched catalog. This also guards against instructions hidden in
       invoice text. If a group's answer breaks these rules or can't be read, the group is sent once
       more. Any line still without a valid result is recorded as "no match", with the reason shown
       ("the AI's answer for this line could not be used").
     - **When a group fails:** if a call errors or times out, that group is retried twice. If it
       still fails, the lines that succeeded are kept, the invoice goes to matching failed, and Retry
       reruns only the lines without a result.
- **Price flags** are worked out by code after matching. Any difference, to the cent, between a
  line's unit price and its catalog item's unit price is flagged, showing both prices and the
  difference. The line amount is covered only by the extraction arithmetic check. Flags are
  recomputed whenever a line's match changes, from an override or from marking it unmatched (which
  clears the flag), and the finalize summary always uses the current flags. A catalog
  price of zero or blank means no fixed price and is not flagged (from the decision on price flags,
  D5).

### The invoice's status

Each invoice moves through these statuses. Before a step starts, it claims the invoice by changing
the status in a single database update that only succeeds if the status is still the expected one
(for example, from awaiting confirmation to matching). A second request that arrives at the same
time, such as a double-clicked Confirm or a repeated Retry, loses that claim and is refused, so a
step can never run twice at once:

1. Uploaded, then Extracting (Claude is reading the file).
2. Awaiting confirmation (metadata suggestions are shown).
3. Matching (line matching is running, and lines fill in as their results arrive).
4. In review (the user can override matches).
5. Finalized (locked).

There are also two failure statuses, extraction failed and matching failed, each with a Retry
button. When the app starts, any invoice still marked Extracting or Matching has lost its running
work, so it is moved to its failure status (Extracting to extraction failed, Matching to matching
failed) and its Retry button appears. From awaiting confirmation or in review the user can go back and change the metadata. That
clears the line matches and overrides after a warning, and matching runs again (from the decision on
going back after matching, D4). Finalized invoices cannot change.

### Screens

1. **Upload:** pick one file (PDF, PNG, JPEG or WebP, up to a size limit set in the spec), plus a
   list of past invoices with their status.
2. **Confirm metadata:** the extracted values next to the suggested sponsor, study and site, each
   with its confidence level and reasons, and a picker to choose a different one. The study picker
   only lists the chosen sponsor's studies. One Confirm button.
3. **Review lines:** a table of every line with its suggested catalog item, confidence, reason and
   price flag. Unmatched lines stand out, and a summary shows the counts. Each line has a searchable
   picker to override its match or mark it unmatched. Lines a person changed are marked, and the
   AI's original suggestion is kept (from the decision on what review lets the user change, D3).
4. **Finalize:** a summary such as "3 lines unmatched, 2 price differences" that the user confirms,
   which is then saved. A finalized invoice shows a "Download JSON" button (from the decision on
   finalizing, D6). The file holds the invoice number and date, the file name, the confirmed sponsor,
   study and site, the extracted total and arithmetic warnings, and every line with its extracted
   values, the AI's original suggestion, any override, the final catalog item or "no match", the
   price flag, and the saved finalize summary with its time.

### Latency

Extraction and matching run in the background inside the app, and the page asks for progress every
second or so: "Matching line items: 12 of 27 done". The logged time runs from when the server
receives the Confirm request until the last line's result is stored. The page's once-a-second
refresh can add up to about a second before the user sees it. It is logged for every run. The README reports first and repeat
runs for each sample. The target is under 30 seconds for the large invoice, measured rather than
promised (from the decision on latency, D9).

### Tests

Most tests use a stand-in for Claude and for the reference API that returns saved answers, so they
are fast, free and repeatable. They cover statuses and the gate, paging, metadata matching, price
flags, overrides and finalizing. A separate set, marked so it runs only on request, calls the real
Claude on the four sample invoices and checks the results against the expected results (from the
decision on test stand-ins, D10). The test command is `pytest`.

## Out of scope

- Logging in, multiple users, permissions.
- Deploying anywhere beyond the laptop.
- Editing extracted values (descriptions, quantities, prices). The user can only override matches.
- OpenAI or any second AI provider.
- Several files per upload, or file types other than PDF, PNG, JPEG and WebP.
- Sending finalized invoices to any payment or accounting system.
- A job queue that survives restarts; a restart during matching needs a Retry click.
- Changing the reference API beyond the one-line fix already made.

## Success Criteria

- **Gate:** calling the line-matching step on an invoice that isn't confirmed is refused by the
  server, which a test proves.
- **Simple invoice:** Contoso Therapeutics, CATALYST Trial and Willow Creek Clinical Research Center
  suggested as exact or likely, and all 5 lines matched to the expected catalog items with no price
  flags.
- **Medium invoice:** Northwind Pharma, LUMIN-2024 and Harborview Medical Institute, all 11 lines
  matched, and exactly one price flag (IRB fees, $550 against $500).
- **Large invoice:** both pages read, all 27 lines extracted, 24 lines matched to the expected items,
  the CT scan price flagged ($475 against $450), and parking reimbursement, patient stipend and
  translator services marked as having no match.
- **Mismatched-metadata invoice:** the right sponsor, study and site suggested but not as exact,
  with reasons naming the sponsor name difference, the protocol year and the site name, then all 7
  lines matched once the user confirms.
- **Images:** a PNG of the simple invoice gives the same results as the PDF.
- **Latency:** the time for the large invoice is measured and reported, aiming for under 30 seconds.
- **Running it:** a reviewer can go from a fresh clone to the upload screen with `docker compose up`
  and an API key, following only the README.

- **Delivered as source code** in the public repositories, run with Docker Compose. The app is added

- **Settings** come from `.env`. `.env.example` lists them: `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`

- **No build pipeline** (continuous integration) is planned for five days. Tests run locally with
  `pytest`.

## Open Questions

Bigger ideas, deliberately kept out of the chosen approach:

- **Learning from overrides:** feed past overrides for the same sponsor and study back into the
  matching prompt as examples, so the app stops repeating a mistake a person has already fixed.
- **A second AI provider:** add OpenAI behind a setting, so a reviewer with only an OpenAI key can
  run it. This is the strongest candidate for the write-up's "one thing I would add next".
- **Shortlisting for huge catalogs:** for catalogs of thousands of items, shortlist candidates by
  text similarity before Claude chooses.
- **Editing extracted values** with totals recalculated, for when Claude misreads a number.
- **A job queue that survives restarts**, if this ever runs for real users.
- **Batch upload:** drop in a month of invoices and work through a review queue.

## Glossary

- **Sponsor:** the drug company paying for a clinical trial, such as Northwind Pharma.
- **Study and protocol number:** one clinical trial and its official ID, such as LUMIN-2024 and
  NWD-LUM-2024-001.
- **Site:** a hospital or clinic that runs a trial and sends invoices to the sponsor.
- **Catalog:** the approved billable items and prices for one sponsor and study.
- **Line item:** one billed row on an invoice: description, quantity, unit price and amount.
- **Reference API:** the provided read-only web service that serves sponsors, studies, sites,
  study-site links and catalogs.
- **Metadata:** an invoice's header facts: sponsor, study, protocol, site, invoice number and date.
- **Hard gate:** a step that cannot be passed until a person acts; here the server, not just the
  screen, refuses to run line matching before confirmation.
- **Structured outputs:** a Claude feature that makes its answer JSON in a shape we define.
- **Prompt caching:** Claude reusing the unchanged start of a prompt between calls, which is faster
  and cheaper.
- **Fuzzy text comparison:** scoring how similar two pieces of text are when they are not identical.
- **Confidence level:** how sure the app is about a match. Metadata uses exact, likely, uncertain or
  not found; line matches use high, medium or low.
- **Atomic status change:** a single database update that only succeeds if the status is still what
  the step expects, so two requests at once cannot both start the same step.
- **Docker volume:** storage that Docker keeps outside a container, so data survives the container
  being recreated.
- **Override:** a person's choice that replaces the AI's suggested match, stored next to the
  original suggestion.
- **Status:** a label stored on each invoice that decides which step may run next.
- **Stand-in (mock):** a fake version of Claude or the reference API used only in tests.
- **FastAPI:** a Python library for building web servers and APIs.
- **htmx:** a small JavaScript library that lets a server-rendered page refresh part of itself.
- **SQLite:** a database kept in a single file, with no separate server.
- **Docker Compose:** a tool that starts several programs (here, the reference API, its database and
  our app) together from one file.
- **Pagination:** an API returning a long list in pages, so the caller must ask for each page.
- **Latency:** how long the user waits for a result.
- **On-screen time:** the headline latency figure, from when the server receives Confirm until the
  page has shown every match.
- **Stored time:** the time from Confirm until the last match is saved, recorded beside the on-screen
  time.
- **Note (arithmetic):** a message that an arithmetic check was skipped, such as no printed total;
  shown with the warnings but not counted as one.
- **Playwright:** a tool that drives a real web browser from test code.
