Architecture: AI Invoice Ingestion Platform

Summary

The problem. A clinical trial site sends an invoice to the drug company paying for the trial (the sponsor). Someone has to tie the invoice to the right sponsor, study and site, and check each billed line against the approved items and prices for that sponsor and study (the catalog). The take-home brief adds one hard rule: line items may only be matched after a person has confirmed the sponsor and study, because those decide which catalog applies.

The approach. One Python web app, built with FastAPI and plain server-rendered pages, runs as a third container next to the provided reference API and its Postgres database. It keeps its own data in an SQLite file on a Docker volume. Claude (claude-opus-5-5) reads each uploaded file and later suggests a catalog item for each line. Matching the invoice's header facts to sponsors, studies and sites is ordinary code. Every step is guarded by a stored status on the invoice, and the server refuses any step whose status is wrong, which is what makes the confirmation gate real.

Where the project stands. The intent (docs/DESIGN.md, tagged tortoise/ideas) and the spec (docs/SPEC.md, 63 requirements, tagged tortoise/spec) are approved. This document is the architecture, approved and tagged tortoise/architecture. All four milestones are built: the app skeleton, database, reference API client, status guard, upload screen, Claude client, extraction, metadata suggestions, the confirmation gate, line matching, price flags, the review screen, finalizing, the JSON download, the live tests and delivery.

Requirements are referred to by name with their spec number in brackets, such as "the gate refusing early matching (R28)".

Eleven parts, each one module (section 12 gives the file names):

  1. Web pages and form handlers show each screen and receive the user's actions.
  2. Status guard is the only code that changes an invoice's status. It checks that the requested

action is allowed from the current status and claims the invoice in one database update (the one-at-a-time claim, R29).

  1. Background runner runs claimed work after the page has answered, so the browser never waits

on Claude.

  1. Extraction step sends the uploaded file to Claude and stores what comes back.
  2. Metadata matching step suggests a sponsor, study and site with confidence levels and reasons,

in plain code.

  1. Line matching step groups the lines, asks Claude for matches, checks every answer and stores

results as they arrive.

  1. Price flag and arithmetic checks compare prices and add up amounts, in plain code.
  2. JSON export builds the download for a finalized invoice.
  3. Reference API client is the only code that calls the reference API, and always fetches every

page. Each request times out after 10 seconds; a connection failure, a timeout, any error answer other than "not found" for a single record, or an answer that isn't JSON raises a "reference API unavailable" error naming the address.

  1. Claude client is the only code that calls Claude. It applies timeouts and retries and

records token counts.

  1. Data store holds the SQLite tables in section 3.

The pages also read the data store directly to draw each screen; that arrow is left out to keep the diagram readable.

3. Database diagram

The app's own database is one SQLite file. SQLite has no exact decimal type, so every money value is stored as text holding an exact decimal such as 550.00, and converted to Python's Decimal on the way in and out (the exact-money rule, R15). Values are never rounded when saved: 550 is stored as 550.00, and a value read with more decimal places keeps them. The diagram shows the column types the code creates; SQLite stores VARCHAR and TEXT alike as text, BOOLEAN as 0 or 1, and FLOAT as a real number. Times are stored as text in ISO 8601 format, such as 2026-10-21T14:03:12.481Z, with milliseconds.

This shows the seven tables and how they link. Every table has its own id. The database also enforces these uniqueness rules, so the "at most one" links can't be broken by a bug: one extraction per invoice, one suggestion per field per invoice, one line per position per invoice, one catalog snapshot row per catalog item per invoice, and one match per line. Quantities are stored as numbers (the numbers rule, R15) and turned into exact decimals before any arithmetic. In words:

  • Each invoice has at most one extraction (one reading of its file).
  • Each invoice has any number of line items; each line item belongs to exactly one invoice.
  • Each invoice has up to three metadata suggestions, one each for sponsor, study and site.
  • Each invoice keeps a snapshot of the catalog it was matched against, so overrides, price flags and

the JSON download never depend on the reference API still answering, and stored catalog IDs can be checked against it (the stored-ID check, R40).

  • Each line item has at most one line match, which holds both the AI's original suggestion and any

override side by side (the override rule, R47).

  • Each invoice has a list of runs, one per extraction or matching attempt (the timing

record, R51).

Going back to change the metadata (the going-back rule, R32) deletes that invoice's line matches and catalog snapshot, keeps its line items and extraction, and its runs stay as history.

4. Request flows

4.1 Uploading and reading an invoice

sequenceDiagram
    actor U as Person
    participant P as Web pages
    participant G as Status guard
    participant R as Background runner
    participant C as Claude client
    participant M as Metadata matching
    participant A as Reference API client

    U->>P: 1. uploads one file
    P->>P: 2. checks size, type from contents, then image size or PDF pages
    P->>P: 3. saves the file, creates invoice in extracting status
    P-->>U: 4. redirects to the invoice page
    P->>R: 5. starts extraction in the background
    R->>C: 6. sends the file, asks for fixed JSON
    C-->>R: 7. returns header, total and lines
    R->>R: 8. runs arithmetic checks, stores the reading
    R->>M: 9. asks for sponsor, study, site suggestions
    M->>A: 10. fetches sponsors, studies, sites, links
    A-->>M: 11. returns every page of each list
    M-->>R: 12. returns suggestions with reasons
    R->>G: 13. moves status to awaiting confirmation

This shows what happens from upload until the confirmation screen is ready.

  1. The person picks one file on the upload screen.
  2. The page handler refuses a request holding more than one file (422), reads at most 10 MB plus one

byte, and checks the 10 MB limit, the type from the file's first bytes, then the 7 MB image limit or, for PDFs, the 20-page limit and that the PDF opens without a password (the upload checks, R7 and R8). A failure answers at once with HTTP 413 for too large, 415 for a wrong type, or 422 for an unreadable PDF, and nothing is stored.

  1. The file is saved under a generated name (the safe storage rule, R9) and a new invoice row is

created directly in the extracting status.

  1. The browser is sent to the invoice page, which shows "Reading your invoice…" and asks for progress

about once a second.

  1. The status guard hands the extraction to the background runner.
  2. The Claude client sends the file as a document (PDF) or an image, with the fixed answer shape

(section 6), and a 120-second timeout.

  1. Claude returns the header facts, the printed total, the yes-or-no "is this an invoice" answer and

every line.

  1. The arithmetic checks run, then the reading and its warnings are stored (the arithmetic rule, R16).

Each line's quantity times unit price is rounded to the cent before it is compared with the amount. A line with a missing quantity, unit price or amount gets the warning "Line N: this line's arithmetic couldn't be checked because a number is missing.", and the total check leaves out lines with no amount and says how many. Money printed with currency codes or symbols (such as USD 2,230.00 or €475) or as an accounting negative ((50.00)) is read normally; a value that still can't be read as a number is stored as missing with a warning quoting how it was printed, and an unreadable printed total is reported as such rather than as "no total printed". If Claude said it is not an invoice, the status becomes extraction failed instead (R13). A Retry's reading is timed from when Retry was pressed; the first reading from the upload.

  1. Metadata matching starts straight away, in the same background job.
  2. It fetches all sponsors, studies, sites and study-site links through the reference API client.
  3. The client keeps asking for pages until it has all of them (the paging rule, R34).
  4. Suggestions with confidence levels and reasons come back (section 7).
  5. The status becomes awaiting confirmation, and the next progress check shows the confirmation

screen.

If Claude errors, refuses or times out, steps 6 and 7 are retried twice and then the status becomes extraction failed (the extraction failure rule, R62). If the reference API fails in step 10, the reading is kept and the status becomes extraction failed with the address that failed (R35); Retry then reruns only metadata matching (R30).

4.2 Confirming metadata (the gate)

sequenceDiagram
    actor U as Person
    participant P as Web pages
    participant A as Reference API client
    participant G as Status guard
    participant R as Background runner

    U->>P: 1. presses Confirm with sponsor, study, site
    P->>P: checks the status first, refusing 409 if not awaiting confirmation
    P->>A: 2. checks the three choices exist
    A-->>P: 3. returns the records, not found, or no answer
    P->>P: 4. checks the study belongs to the sponsor
    alt a check failed or the reference API did not answer
        P-->>U: refuses Confirm, status unchanged
    else every check passed
        P->>G: 5. asks to move to matching
        G->>G: 6. one update, only from awaiting confirmation
        G-->>P: 7. claim won, or refused
        P-->>U: 8. shows progress, or the refusal
        P->>R: 9. starts line matching
    end

This shows the gate: the only way into line matching.

  1. The person presses Confirm. The form sends the chosen sponsor, study and site IDs. The handler first

checks that the invoice is awaiting confirmation, answering 409 otherwise, whatever the choices are. (Opening the confirmation page itself reloads the reference choices; if the reference API doesn't answer, the page shows that error.)

  1. The handler asks the reference API client for each record.
  2. A missing record refuses Confirm with HTTP 422 and a message naming it (the Confirm check, R61).

If the reference API does not answer, Confirm is refused with HTTP 503 and "Couldn't reach the reference API at …; press Confirm to try again". The invoice stays awaiting confirmation; pressing Confirm again is the retry. (The reference API failure rule, R35, covers background steps; Confirm is answered directly, so it needs no failure status.)

  1. If the study's sponsor is not the chosen sponsor, Confirm is refused the same way.
  2. The handler asks the status guard to move the invoice from awaiting confirmation to matching.
  3. The guard runs one database update that changes the status only if it is still awaiting

confirmation, and also stores the confirmed IDs and names (the one-at-a-time claim, R29).

  1. If no row changed, someone else claimed it or the status was wrong: the handler answers HTTP 409

Conflict naming the current status (the gate refusing early matching, R28). A double click lands here.

  1. Otherwise the browser is sent to the review page, which shows "Matching line items: 0 of N done".
  2. The guard hands line matching to the background runner, recording the time the request was

received as the start of the matching run (the timing record, R51).

Warnings while choosing. Whenever the person changes the sponsor, study or site picker, the page asks the server to redraw the warnings for the current choice: the site not being linked to the study (the cross-check, R22) and an earlier upload with the same invoice number whose site is currently confirmed as the same one (the duplicate warning, R25). Neither warning blocks Confirm.

There is no other route that starts matching. Retry from matching failed uses the same guard, with matching failed as the only allowed starting status.

4.3 Matching line items

sequenceDiagram
    participant R as Background runner
    participant A as Reference API client
    participant L as Line matching
    participant C as Claude client
    participant F as Checks and price flags
    participant S as Data store

    L->>A: 1. fetches the confirmed catalog, every page
    A-->>L: 2. returns all catalog items
    L->>S: 3. saves the catalog snapshot
    R->>L: 4. hands lines without a result
    L->>C: 5. counts tokens in the shared prompt start
    L->>C: 6. sends the first group alone if cacheable
    L->>C: 7. sends the other groups, five at most at once
    C-->>L: 8. returns one answer per group
    L->>F: 9. checks each answer, then asks for price flags
    L->>S: 10. saves each accepted line's result and flag
    R->>S: 11. sets in review, or matching failed

This shows how matches are produced and saved as they arrive.

  1. On a first run, line matching fetches the catalog for the confirmed sponsor and study, with

page_size=200, until every page is in (the paging rule, R34). The large catalog is 100 items. If the reference API doesn't answer, the invoice goes to matching failed with the address named. On Retry, steps 1 to 3 are skipped when a snapshot was saved, and the saved snapshot is used, so every line on the invoice is matched against the same catalog.

  1. All items come back.
  2. They are saved as the invoice's catalog snapshot (section 3). Changing the metadata deletes the

snapshot, so the next confirmation fetches a fresh one.

  1. The lines that have no result yet are handed to line matching, in invoice order. On a first run

that is every line; on Retry it is only the missing ones (R30).

  1. Line matching asks Claude's token-counting endpoint how long the shared prompt start is (the

instructions plus the catalog).

  1. If it is at least the model's minimum cacheable length and there is more than one group, the

first group of up to six lines is sent alone so it writes the cache (the batching rule, R37). The run records the cache as used only if that first request succeeded. If counting fails, or the prompt is too short, this step is skipped.

  1. The remaining groups are sent at the same time, at most five requests at once.
  2. Each request returns one structured answer for its group (section 6).
  3. Each answer is checked: one result per line, every catalog ID (including alternatives) in the

snapshot, at most two alternatives (R40). Accepted lines are kept; only the lines whose answers failed the checks are sent once more, as one request. Price flags are then worked out (R43, R44). (Separately, the Claude client already tries up to three times for errors and unreadable answers, section 6; this resend is for answers that arrived but named lines or items wrongly.)

  1. Each accepted line's result and flag are saved straight away, so the next progress check shows

it (R42). Each save checks, in the same write, that the invoice is still matching; if the user changed the metadata meanwhile, the late result is discarded and their change stands.

  1. When every line has a result, the status becomes in review and the stored time is recorded. If

any line is still without one, the status becomes matching failed with the reason (R40, R41), and the run's stored time stays empty, since no "last result" moment exists. An unexpected error in a group (such as a database lock) is caught in that group, so the run's counts and reason are still recorded. The matching-failed screen lists every line, marking those without a result.

4.4 Overriding a match

sequenceDiagram
    actor U as Person
    participant P as Web pages
    participant G as Status guard
    participant F as Price flags
    participant S as Data store

    U->>P: 1. types in a line's picker
    P->>S: 2. searches the catalog snapshot
    S-->>P: 3. returns items matching the text
    U->>P: 4. chooses an item or No match
    P->>G: 5. checks the status is in review
    G-->>P: 6. allowed, or refused if finalized
    P->>F: 7. recomputes the line's price flag
    F->>S: 8. saves override and flag
    P-->>U: 9. redraws the line and the summary

This shows a person replacing the AI's choice for one line.

  1. The person types in the picker on a line.
  2. The page searches that invoice's catalog snapshot by code and description.
  3. Matching items come back as a short list.
  4. The person chooses an item, or "No match".
  5. The handler asks the status guard to save the override. The guard opens one database

transaction that first re-reads the status with a write lock and only continues if it is in review.

  1. Any other status ends the transaction with HTTP 409; a finalized invoice can never change (R33).

Because the check and the write share one transaction, a Finalize arriving at the same moment either happens first (and the override is refused) or waits until the override is saved.

  1. Inside the same transaction, the price flag is recomputed for the new choice (R45). "No match"

clears it.

  1. The override is saved beside the AI's original suggestion (R47), and the transaction commits.
  2. The page reloads at that line, with the summary updated. Undo is the same flow with the override

removed. Choosing the AI's own suggestion counts as no override. Each picker starts on the line's current item, and search results start with "Choose an item…", which the server refuses, so pressing Change without choosing never changes a match.

This shows finalizing with acknowledged open problems, then the download.

  1. The person presses Finalize on the review screen.
  2. The page counts no-match lines, price flags and arithmetic warnings, using current values.
  3. The summary is shown, such as "3 lines with no match, 1 price difference, 0 arithmetic warnings"

  1. The person confirms it. The form sends back the counts it showed.
  2. The status guard claims the move from in review to finalized. If the counts sent back no longer

An unknown invoice answers 404, one not yet finalized 409.

6. How Claude is called

Both calls go through the Claude client, which uses the official anthropic Python library.

  • Model comes from ANTHROPIC_MODEL, default claude-opus-5-5.
  • Answer shape. Both calls use Claude's structured outputs (client.messages.parse with a Pydantic

model), so the answer is checked against our shape before our code sees it.

  • Effort. claude-opus-5-5 always thinks a little and cannot have thinking turned off, so effort

is the speed control. Extraction starts at medium and line matching at low. The live tests measure both, and the effort can be raised if accuracy falls short.

  • Unusable answers. A refusal, an answer cut off at the token limit, or an answer that doesn't

fit the shape counts as failed and goes through the same retry rules as an error. A failed call still counts as a request in the run's numbers, and the reason shown never repeats the error's own text.

  • Prompts. The extraction instructions live in app/prompts/extraction.md, and the matching

instructions in app/prompts/matching_instructions.md.

  • Timeouts and retries. The anthropic library's own retries are turned off, so these are the

total. Extraction: 120 seconds per call; matching: 60 seconds per call; each followed by up to two more tries after waits of 1 and 3 seconds (R62, R41). A request the API rejects as invalid (an HTTP 4xx other than 408, 409 or 429) is not retried, since it would fail the same way. Every request sets max_tokens=16000.

  • Usage. Every answer's token counts are added to the current run (R51).
  • The key is read once from ANTHROPIC_API_KEY at startup and is never logged or stored (R4).

The extraction call sends one user message holding the file (a document block for a PDF, an image block for an image) and a short instruction. The answer shape has the header fields, the printed total, the "is this an invoice" answer and the list of lines. Every field allows null for "not printed" (R12). Money is returned as text such as "550.00" and converted to exact decimals.

The matching call has three parts:

  1. The system prompt: fixed instructions, including that invoice text is data and never

instructions (R38), and that price only breaks ties (R39).

  1. The catalog, in a fixed order, with each item's ID, code, description, category and unit price.

The end of this block carries Claude's cache marker, so everything up to here can be cached (R38).

  1. The user message: this group's lines as a JSON list, each line a separate object with its

position, description, quantity and unit price, followed by a reminder that every description is data from an untrusted document. Keeping each line in its own field limits how far a hostile description can reach; the hostile-text test (the safety rule, R54) checks that the other lines on that invoice still get their expected catalog items.

The answer shape is a list of results, each with the line's position, a catalog item ID or null for no match, high, medium or low confidence, a one-sentence reason, and up to two alternative IDs.

Estimated timing for the large invoice (to be checked by measurement): 27 lines make 5 groups. If the catalog is too short to cache, all 5 go at once and finish in roughly the time of the slowest one. If it can be cached, one group goes first, then four at once, which is about two calls' time. With calls taking roughly 8 to 15 seconds at low effort, both fit inside the 30-second target.

7. Metadata matching rules

All comparisons first clean the text: lower case, accents removed, punctuation removed, spaces collapsed.

  • Exact means the cleaned text is identical (for a name; a sponsor's short code also counts), or

the protocol number is identical. Company endings are not removed for this test, so "Northwind Pharmaceuticals Inc." is never exact for "Northwind Pharma" (R19).

  • Fuzzy score. For likely and uncertain, the app also removes common company endings ("inc",

"ltd", "llc", "co", "corp", "company", "pharmaceuticals", "pharma", "therapeutics", "biopharma", "life", "sciences") and scores similarity with the rapidfuzz library's token set ratio, from 0 to 100.

  • Starting thresholds, tuned by the tests: 85 or more is likely; 60 to 84 is uncertain; below 60

is not found. Likely also needs a lead of at least 10 points over the second-best candidate.

  • Protocol numbers are compared segment by segment, split on hyphens. A protocol that differs from

a real one in exactly one segment is likely, and the reason names that segment ("differs in the year" when the segment is a four-digit year) (R20). The study name is always scored too: a name that points clearly to a different study lowers an exact protocol match to likely, and a one-segment near miss to uncertain, with the conflict named. A study with no protocol match is scored by name alone.

  • Sites add supporting evidence to the name score: the same city and state, and the same

principal investigator surname. Two facts together, or one fact with a name score of at least 60, move the confidence up one level, at most to likely (R21). An exact site name whose printed city, state or investigator disagrees with the record is likely, not exact, with the disagreement named.

  • Cross-checks then run as the spec describes (R22): study against sponsor; sponsor taken from

the study (never rated above the study's own level); and a site not linked to the study lowering the site's confidence by one level. The confirmation screen shows the site-link and duplicate warnings as soon as it loads, and redraws them when a picker changes.

Every expected example in the spec (R19, R20, R21 and the four sample invoices) is a unit test, so the thresholds can be tuned without guessing.

9. Background work and retries

flowchart TD
    claim["Status guard claims the invoice"]
    task["Background task starts"]
    askclaude["Call Claude"]
    ok{"Answer usable?"}
    retry{"Retries left?"}
    save["Save results"]
    fail["Set the failure status with the reason"]
    advance["Set the next status"]

    claim -->|"claimed work"| task
    task -->|"one request"| askclaude
    askclaude -->|"answer or error"| ok
    ok -->|"yes"| save
    ok -->|"no"| retry
    retry -->|"yes, wait then resend"| askclaude
    retry -->|"no"| fail
    save -->|"all work done"| advance

This shows the retry loop every Claude request goes through, inside one background task.

  • The runner uses FastAPI's background tasks, which run in the app's own process after the page has

answered. Line matching runs its groups in a thread pool of five workers, giving the "at most five at once" rule (R37). Each worker uses its own database session.

  • SQLite runs in write-ahead logging mode so the page's progress reads never block the workers'

writes.

  • Retry counts and timeouts are in section 6. "Answer usable" means it arrived, was not a refusal, and

passed the shape and catalog checks.

  • Every background job runs inside a catch-all. Any error that isn't a handled Claude or reference

API failure, such as a missing stored file or a database error, sets the running step's failure status with the reason "Unexpected error (<error type>); details are in the app log" and is logged, so an invoice never stays in extracting or matching while nothing is running. A missing stored file gives the reason "The uploaded file is missing; please upload it again", since Retry cannot fix that.

  • When the app starts, before taking any requests, it moves every invoice still in extracting or

matching to its failure status with "Interrupted by an app restart" (R31). Background tasks do not survive a restart, which the spec accepts.

This shows the seven statuses (R27) and every allowed move between them. The status guard holds this table in code, and any move not shown is refused with HTTP 409. Every write that depends on the status (claims, overrides, undo, changing metadata, finalizing) checks the status inside the same database transaction as the write, never in a separate read beforehand. Changing metadata from awaiting confirmation only changes the pickers, so it is not a status move. While the status is matching, metadata cannot be changed (R32).

15. Trade-offs and what to revisit

  • Background work in the app process keeps the build to one container, but work is lost on a

restart. Restart recovery turns that into a Retry button. Revisit with a job queue if this ever has real users.

  • Metadata matching in code is free, fast and unit-tested, but its thresholds are hand-tuned on

eight sites and six studies. Revisit with Claude as a judge of close calls if the reference data grows.

  • The whole catalog in every matching call is simple and lets Claude see every option, but it

grows with the catalog. Revisit with a text-similarity shortlist for catalogs of thousands of items.

  • SQLite needs no server and suits one user, but allows one writer at a time. Fine here; revisit

for several users.

  • Polling about once a second is simpler than streaming updates, and costs at most a second of

delay, which the on-screen time includes honestly.

Glossary

  • Sponsor, study, site: the drug company paying, the trial, and the hospital or clinic that bills.
  • Catalog: the approved billable items and prices for one sponsor and study.
  • Catalog snapshot: the copy of a catalog saved with an invoice when it is matched.
  • Reference API: the provided read-only web service holding sponsors, studies, sites and catalogs.
  • Status guard: the one piece of code allowed to change an invoice's status.
  • Claim: changing the status in one database update that only succeeds from the expected status,

so two requests can't both start the same step.

  • Background task: work the server carries on with after it has already answered the browser.
  • Thread pool: a fixed set of workers that run tasks side by side; here, five.
  • Write-ahead logging (WAL): an SQLite mode that lets readers and a writer work at the same time.
  • Structured outputs: Claude answering in a JSON shape we define and check.
  • Effort: a Claude setting that trades thinking depth for speed.
  • Prompt cache: Claude reusing the unchanged start of a prompt, when the request marks where the

reusable part ends and it is long enough.

  • Token: a small chunk of text used to measure and bill Claude's input and output.
  • Token set ratio: a fuzzy score from 0 to 100 that compares the words two texts share.
  • Polling: the page asking the server for news at a fixed interval.
  • htmx: a small script that lets a server-rendered page refresh one part of itself.
  • Jinja2: the template language that turns data into HTML pages.
  • SQLAlchemy: a Python library for working with databases through Python classes.
  • Docker Compose: a tool that starts several containers together from one file.
  • Docker volume: storage that survives a container being recreated.
  • HTTP 409, 413, 415, 422: the web's codes for "conflicts with the current state", "too large",

"unsupported file type" and "values are invalid".

  • ISO 8601: the standard way of writing dates and times as text, such as 2026-10-21T14:03:12Z.
